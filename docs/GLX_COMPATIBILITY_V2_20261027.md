### 代码直接证明的行为

冻结场景：`E:/AI/wechat-wasm-slim/.local/glx-ios-functional-20261027-03/scene-source/main.gd`，SHA256 `e4f6c196e1d03f3706c2b9f1526df4b20493c332c0693bad825068964c0bf0b3`；与当前仓库源码一致。

固定引擎源码根：`E:/AI/wechat-wasm-slim/.local/glx-godot-newlib-build-20261026-02/build/engine`；候选 sourcePin `df3cdd9bc9941a20cb5575d781cde6f937637bcb`，沿用原构建补丁与官方新库，不换依赖。

1. `main.gd:153–195` 先 remove_child／queue_free 旧页，再在同一次调用里建立新页。queue_free 是延迟删除；`scene/main/scene_tree.cpp:735,1626–1634` 在处理末尾清理队列。不能把这一过程理解为旧页资源全部释放完才开始新页。
2. 新 cube 设置 material_override（`main.gd:330`）时，`scene/3d/visual_instance_3d.cpp:218–226` 立即调用材质 get_rid；`scene/resources/material.cpp:3124–3127` 立即执行 _update_shader。`material.cpp:681–690` 找到相同 key 会复用 shader 并增加 users。这使直接 3D→3D 的交接能发生在旧材质析构前。
3. `material.cpp:3982–3993` 在最后一个材质使用者消失后 free_rid 并删除 shader_map 项；`drivers/gles3/storage/material_storage.cpp:3239–3242` 释放其 version，`drivers/gles3/shader_gles3.cpp:720–736,787–791` 清理相应 GL shader/program。因此 shader_map 不是所有历史材质永久保留的缓存。底层驱动是否另有缓存、是否命中仍未知。
4. 第 6、8、9 页及第 7 页方块共用同一种材质配置；第 7 页额外两个 QuadMesh 使用 ALPHA 和 CULL_DISABLED（`main.gd:295–345`）。两个透明片颜色不同，不代表必然各编译一套独立 shader；区别是透明配置与不透明配置不同。
5. `shader_gles3.cpp:739–754` 新 version 先尝试缓存，未命中时编译；`shader_gles3.h:189–203` 首次绑定或缺 specialization 可当场编译。这里只能证明同步工作路径存在，不能证明本次具体命中了哪条。
6. 各 3D 页都新建视口、世界、相机、贴图、材质、网格和灯。贴图由 GDScript 像素循环生成再上传（`main.gd:203–221`）；这些也可能贡献耗时。不过 8↔9 改变视口数量仍不卡、7→6 释放更多透明资源仍不卡，削弱了“只因 FBO 创建”或“只因释放旧资源”的单一解释。

### 与“3D 预热”的关系

当前全局 RasterizerSceneGLES3 构造时执行默认 scene shader 的初始化和绑定（`drivers/gles3/rasterizer_gles3.cpp:384`、`rasterizer_scene_gles3.cpp:4529,4616–4618`）。翻页只创建场景资源，不重新创建 rasterizer，**不是每翻一页都重跑这段启动预热**。这段默认初始化也不代表已经准备所有透明／贴图材质。

Godot 官方明确将 Compatibility 与 Forward+/Mobile 的现代 pipeline 预编译机制区分；当前 GLES3/GLX 路线不能照搬后者的预编译开关。[官方说明](https://docs.godotengine.org/en/4.6/tutorials/performance/pipeline_compilations.html)

因此不优先关闭默认预热，也不为此重编引擎；它没有直接解决“最后使用者释放后再创建”的依据。当前成功引擎没有可直接使用的 skip_default_3d_prewarm 开关，保留原结论。

## 最小单变量验证：仅延长有限材质引用的寿命

用户已回答“第 9 页内部重建也卡”，无需再次要求重复这组现有操作。下一项如需确认机制，使用 03 冻结源码的独立派生，**只额外保留已实际创建的不透明材质和透明材质各一个强引用**，到会话结束释放。节点、视口、每次新材质／贴图的创建流程、相机、提交和代码路径仍按原样执行；不提前渲染、不手工提交、不加延迟，不改变默认成功包。

这不是完整性能修复或默认优化。保留材质也会保留它引用的纹理，必须记录额外存活资源的有限范围，不能宣称“只保留 shader、零内存成本”；也不能用节点消失证明 GPU 内存释放。

- 预期：首次进入仍可能顿；若以后 5→6、6→7、离开 7 再回来及第 9 页重建明显减轻，支持“材质及依赖存活／shader 重建”解释。
- 若没有改善，削弱该假设，继续看贴图生成上传、视口建立、驱动/GLX 状态等已有路径，不能继续盲目增加缓存。
- 若只改善一部分，记录对应路径，不把全部卡顿宣布解决。
- 这项实验仍不能独立证明准确 GPU 编译耗时。需要测量时，仅在现有页面动作边界记录事件和有限时间值；first frame callback 不叫“首个可见像素”，CPU 时间不叫 GPU 时间，不追加逐帧海量日志。
- 若实施与上手机，另报精确候选和有限步骤；本轮未实施。新版全面改版不能拿来代替这一单变量对照，因为 UI、场景和资源数量都会变化。

## 新版：目录分组，每个判断都有看得见的标准

可消费的完整中文文案：`examples/glx-ios-functional-v2/cases.json`。目前是设计目录，不是可运行项目或新包。8 张基础卡、3 张稳定性卡，每张按步骤展示，不把全部描述堆到底部。测试重点分三栏：**画面是否正确、操作是否响应、是否有停顿**。画面正常但切入顿一下可以同时成立，不能只留一个总“通过”。

| 基础卡 | 用户看到的动作与标准 | 相对旧版的补齐 |
| --- | --- | --- |
| 图片、中文和半透明 | 对照编号与向上箭头；放大“中文测试，123！”；红圆下面仍看得到棋盘 | 用编号、样句和底纹代替“清晰／自然” |
| 图形不能跑出白框 | 拖条纹穿过边界；框外黄点一直可见 | 同时检查裁剪不足和误裁剪、触摸响应 |
| 面板变大，四角不变 | 分别拖宽／拖高；四个彩角与固定轮廓一样大，角边不裂开 | 水平、垂直单独判定；只用合法尺寸，不把小于边距和的边界行为混入 |
| 边框小砖怎样重复 | 上框砖大小不变，末端允许半块；下框每块完整，宽度略变 | 不要求用户理解 TILE／TILE_FIT；边和中心都检查 |
| 面板透明、换图 | 中心隐藏时透出棋盘；数字角标换成字母，无旧影 | 动态换图、中心开关与透明边缘都有动作和独立结果 |
| 主画面的立体方块 | 方块暂停到编号正面；灯移动后指定面按示意变亮／变暗 | 新增主视口直接 3D；旧版全经 SubViewport。灯光不能只靠“有立体感”判断 |
| 谁在前，谁被挡住 | 透过前方红片能看见方块；后方蓝片被方块挡住，移开后露出 | 固定相机和非共面几何，避免透明排序歧义；贴图／灯光与遮挡分开 |
| 两个小窗口各管各的 | 左边换图时右边先暂停；只转右边时左边先暂停；右窗变大又恢复 | 防止把另一侧正常动画误认串图；新增实际 SubViewport 尺寸变化 |

NinePatchRect 的四角、边和中心规则以 [官方类说明](https://docs.godotengine.org/en/stable/classes/class_ninepatchrect.html) 为依据。平铺参照图要无缝；保留完整砖的方式允许轻微伸缩，不能把这种预期变化判成错误。测试不偷改过滤器／透明策略来获得“漂亮结果”。

稳定性三卡单独执行，不让每次翻页都承担稳定性验收：

1. **持续动，不是只显示一张图**：同一场景前台两分钟，末尾拖动；倒计时结束不自动通过。
2. **回到桌面，再回来**：保持同包，桌面约 10 秒后回来，拖动／换图并观察约 20 秒；hide/show 和用户结果配对，缺日志即未知。
3. **内容清空后能重新出现**：最多三组清空／重建，每组单记显示与停顿；不当成微信重启、实际场景文件切换或无内存泄漏。

- 显示结果：“符合示意／有异常／看不清／未检查”；操作与流畅度各自记录。允许看不清，不强迫猜测。没有人工结果时仍未检查，不因为触发动作或完成倒计时自动通过。
- 异常可选：“空白／缺图缺字／位置或遮挡不对／透明不对／不再运动／按钮无反应／其他”；另记“停一下恢复／一直卡住”，避免把掉帧和黑屏混为一项。
- 状态针对每个小步骤保存。目录给“已观察 5/20 项”等实际计数，不让一个页级按钮覆盖多个未操作项。示意图为独立固定示意，不由同一待测 GLX 路径生成来互相认证；示意也不冒充精确像素基准。
- UI 使用手机安全区、大字、足够触摸尺寸；左右比较不足宽度就上下排，不能把两幅图缩到看不清。vConsole 遮挡时可收起，但不改其实现。
- 开始与摘要保留包、场景版本、引擎／库身份、实际 SDK／模式及会话。逐步日志只记动作与人工结果；有限记录，不加 GPU 回读，不联网发新云报告。
