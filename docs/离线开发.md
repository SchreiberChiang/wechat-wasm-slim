# Windows 离线开发

维护代码位于本仓库。安装版由 `packaging/build-release.mjs` 生成。提交中的 `offline` 同时保存本地开发所需的第三方工具、引擎配对、原始测试材料和配对证据。将整个源码交给下一位开发者时一并保留此目录。此交付含本地使用的官方转换器和 GLX 二进制依赖。

## 初次准备

在独立源码的 PowerShell 窗口运行以下命令，将准备目录设为一个全新路径。脚本核对 SHA-256，展开固定的 Node、Python、Git 和 Godot，并用 Git 检查 c050 与 df3 的提交、目录树和对象完整性。准备目录可以按需重新生成。

```powershell
$work = Join-Path (Split-Path (Get-Location)) 'local-build'
New-Item -ItemType Directory -Path $work
& ./offline/prepare.ps1 -Directory "$work/tools"
& "$work/tools/node.exe" tests/run-offline.mjs "$work/tools"
& "$work/tools/node.exe" packaging/build-release.mjs "$work/release" --write
& "$work/tools/python-3.14.0/python.exe" -IB offline/restore-proof.py "$work/proof"
```

`offline/inputs.json` 给出单个原件的来源、字节数和 SHA-256。`offline/platform/platform.json` 锁定桌面工具包。`offline/proof/pack.json` 锁定证据包，恢复程序还逐文件核对写入后的内容。保守和纯 2D 配对核验使用与 release 并列的 `proof`。原始收据中的旧路径用于解释历史记录，实际读取来自恢复出的目录。

历史收据还绑定了当时审核程序的字节。`offline/pair-review` 保存提交 `aeb9e5f` 的固定运行文件，历史配对工作线程在读取原始收据前验证它们。新功能和新引擎审核仍在顶层的 `lib`、`engine` 和 `convert` 中维护。离线回归把任何失败、跳过或取消都计为未通过。

也可以从 Windows 命令提示符执行 `offline\prepare.cmd 新工具目录`。它用系统自带的 CertUtil 核对 Python 压缩包的固定 SHA-256，再调用 Windows 的 tar 和包内 Python 完成准备。PowerShell 入口也调用这个准备程序。离线引擎构建通过 Windows 性能计数器读取 CPU、可用内存、提交内存和换页指标，继续使用固定配方的资源阈值。

准备脚本为随附的 Godot 编辑器创建独立设置目录，从 c050 提交中的 `thirdparty/certs/ca-bundle.crt` 读取公开 CA 证书包。受限 Windows 用户可从这个编辑器运行导入和导出。安装测试工程后，先在工程设置中启用插件，再导出，插件的导出过滤器会排除面板脚本。

## Claude 面板接入

面板维护入口是 `editor/workbench`，服务入口是 `wxslim.mjs quick`。在工作区运行 `quick requirements full`、`quick requirements conservative` 或 `quick requirements 2d` 可取得模板名、确认字段、移除模块及自动解析的输入。保守版确认未使用七个模块，纯 2D 确认移除 3D 及列出的模块。确认与当次实际导出的 PCK 绑定。

`quick plan` 返回运行前的检查结果。执行使用 `quick run`，查询单次运行使用 `quick status`，列出历史使用 `quick runs`，请求取消使用 `quick cancel`。写入操作仍使用已有的 `--write` 约定。UI 可先独立迭代布局、文案与交互，再对照固定服务版本联调。

导出或转换期间，界面可以显示 `progress.step` 和 `progress.lastEvent` 中最近记录的阶段、状态和时间。首次记录写完前，或日志读取期间发生变化时，`lastEvent` 可能为空。最终结果读取运行的 `status`，取消请求读取 `cancelRequested`。

## 原始样本

首次 c050 转换输出位于 `offline/fixtures/c050/framework.js`。图形修正回归使用的 df3 派生原件位于 `offline/fixtures/df3/emscripten-before-godot-process.js`。历史裁剪构建内的 FAILED 收据按原字节保存。当前开发验收结果记录在独立验收目录。

## 从源码重建引擎与验收配方

先用本仓库内的下载包准备独立 SDK，再运行需要的配方。每次原始构建使用新的空路径。三种配方可共用同一个已经校验的 SDK。

```powershell
& "$work/tools/python-3.14.0/python.exe" -IB engine/official-toolchain.py --root "$work/sdk" --base-python "$work/tools/python-3.14.0/python.exe" --offline-inputs (Resolve-Path ./offline/downloads).Path --jobs 4 --write
& "$work/tools/node.exe" offline/rebuild.mjs full "$work/tools" "$work/sdk" "$work/raw-full" --write
```

配方名为 `full`、`conservative`、`pure-2d`。在 `terminal.json` 中检查原始捕获结果。使用随附配对验收时，下面的命令安装插件、启用导出过滤器、导出示例游戏、调用官方转换器、核验包内文件和配对，并写入 `result.json`。

```powershell
& "$work/tools/node.exe" offline/verify-recipe.mjs full "$work/tools" "$work/release" "$work/check-full"
```

在独立示例游戏里复测面板的拒绝、取消和失败处理：

```powershell
& "$work/tools/node.exe" offline/verify-controls.mjs "$work/tools" "$work/release" "$work/check-controls"
```

程序核对缺少保守配方确认时输出目录为空，在 Godot 已成功导出 PCK 后取消正在运行的转换，然后让示例导出的 PCK 占用预留给收据的空间，核对真实导出任务和面板均显示失败。每一步的退出码、任务收据及最终状态保存在新目录中。

已完成的运行可以用 `quick open RUN --write` 在本机开发者工具中打开；需要绑定 AppID 时传 `--appid-from 工程配置文件`。查询接口返回的 `openTarget` 可用来启用打开按钮。

用新构建的配对做一次真实转换时，先检查示例游戏是否使用该配方移除的功能，再运行以下命令。程序重新审核原始任务、准备胶水、把本次 PCK 及功能声明绑定到配置、调用官方转换器，最后逐文件核对输出。

```powershell
& "$work/tools/node.exe" offline/verify-rebuilt.mjs full "$work/raw-full" "示例游戏导出的启动.pck" "$work/check-rebuilt-full" --confirm-game-features
```

要让安装版直接使用重建的引擎，用含相同引擎配方修改的源码生成安装版。在游戏的 `wxslim-export.json` 中将 `rebuiltPreparation` 指向本次的 `preparation.json`，可使用相对设置文件的路径。面板继续调用 `quick plan` 和 `quick run`。计划会返回原始构建任务编号、配方及实际 WASM 的 SHA-256。保守和纯 2D 仍需确认本次游戏未使用移除的功能。

下面的命令将该安装版装入独立示例游戏，导出一份新 PCK，用指定的重建配对执行官方转换，再核对来源及包文件。三种配方各使用自己的准备文件和输出目录。

```powershell
& "$work/tools/node.exe" offline/verify-recipe.mjs full "$work/tools" "$work/edited-release" "$work/installed-rebuilt-full" --rebuilt-preparation "$work/check-rebuilt-full/preparation.json"
```

10 月的 GLX / WebGL 双包场景重放使用 `offline/stage-reference.mjs`。两套原始母包清单及去重后的内容位于 `offline/fixtures/reference-parents`，保留原包中的本地工程配置，仅供本地使用。工具先按封存清单验证两套母包，再调用原始派生及复核函数。使用下面的入口可在没有旧 E 盘工程的电脑上重放。

```powershell
& "$work/tools/node.exe" offline/stage-reference.mjs examples/simple "示例游戏导出的启动.pck" "$work/reference-packages" --write
```
## 验证实际的引擎源码修改

在用于开发的干净检出中，可以应用仓内的示例补丁。它把 Godot 主循环尚未就绪时的诊断补充为“通知已跳过”，同步更新原始 C++ 补丁、源码准备器及对应的文件指纹。已有安装配对仍可作为字节对照。先用随附 Git 核对补丁能否应用，随后从这份已修改源码重建。

```powershell
$git = "$work/tools/git-windows/mingw64/bin/git.exe"
& $git apply --check offline/examples/engine-diagnostic.patch
if ($LASTEXITCODE) { throw '源码版本与示例补丁不符' }
& $git apply offline/examples/engine-diagnostic.patch
if ($LASTEXITCODE) { throw '示例补丁应用失败' }
& "$work/tools/node.exe" tests/run-offline.mjs "$work/tools"
& "$work/tools/node.exe" offline/rebuild.mjs conservative "$work/tools" "$work/sdk" "$work/edited-conservative" --write
& "$work/tools/node.exe" offline/verify-rebuilt.mjs conservative "$work/edited-conservative" "示例游戏导出的启动.pck" "$work/check-edited-conservative" --confirm-game-features --verify-example-edit
```

正式复验分别选择 full、conservative、pure-2d，并为各次运行指定新目录。最后一条命令核验实际准备好的 C++、历史 WASM 中的原文字和新 WASM 中的修改后文字，再核对实际官方转换、包内文件和来源。结果写入本次的 result.json。

## 在不挂载旧盘的 Windows 环境复验

已有 Windows Sandbox 的主机可用以下命令生成本地配置。先准备两个互不重叠的空目录用于记录和临时构建；另传至少两份在主机上确实存在的旧文件。例如分别选择旧安装版的清单和旧配对的来源文件。命令只生成配置，打开配置后才会启动沙箱。

~~~powershell
& "$work/tools/node.exe" offline/windows-sandbox.mjs prepare $evidence $scratch $oldReleaseManifest $oldPairLocator --write
~~~

该配置请求 20 GiB 来宾内存，禁用虚拟网络和剪贴板，只映射源码、记录目录与临时目录。源码只读映射在 C:\GLXSource。进入沙箱后，在命令提示符运行以下命令。环境检查实际尝试打开旧路径，核对源码映射的写权限及非环回网络接口，并在 guest-isolation.json 中记录来宾可见的处理器数和内存。

编译前在来宾内核对固定配方的资源要求，包括至少 11 个可用逻辑处理器、至少 12 GiB 且占总量 40% 的可用物理内存、8 GiB 提交余量，以及配方预算以外的 2 GiB 磁盘预留。实际 CPU 负载也会计入预检。可在满足这些条件的隔离 Windows 虚拟机中完成 SDK 和引擎重建。环境隔离与编译结果各自保留收据。

~~~bat
C:\GLXSource\offline\prepare.cmd C:\GLXScratch\tools
C:\GLXScratch\tools\node.exe C:\GLXSource\offline\windows-sandbox.mjs guest-check
~~~

验收已修改的引擎时，向来宾只读映射已经应用示例补丁的独立源码检出。已准备的临时目录、过往日志和旧安装版均不作为输入。使用已有的断网 Windows 虚拟机也可采用相同映射和检查步骤。

完整交付复验可在新来宾的命令提示符中一次运行。主机先将示例引擎补丁应用到要映射的源码，在来宾中使用全新的临时目录和证据目录。证据目录初始只包含主机生成的探针清单及可选的沙箱配置。

~~~bat
C:\GLXSource\offline\verify-guest.cmd
~~~

该入口自动准备工具，实测旧路径和网络隔离，运行完整回归，从源码生成安装版，依次验证三种随附配对、拒绝、取消及导出失败。随后它在来宾内准备 SDK，重建三种修改过的引擎，再分别安装插件、重新导出示例 PCK、使用对应新配对执行官方转换。结束前再次实测隔离条件。全部通过时，证据目录的 `DELIVERY-RESULT.json` 记录两组包身份、实际 WASM 指纹、任务编号和回归统计。执行过程中的错误会保留各阶段的日志。
