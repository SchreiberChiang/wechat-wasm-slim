## 电脑侧时钟合同核查

查到一条明确的静态单位风险：固定 adapter `weapp-adapter.js:221–224` 定义 `performance.now() = Date.now()/1000`，给出 epoch 秒；导出和注入路径见 109–119 与 87–91。生成 JS 中 `_emscripten_get_now=()=>performance.now()`（字符偏移 10941），本例 `main.cpp:56` 再将其除 1000 后转 float。

[Emscripten API 合同](https://emscripten.org/docs/api_reference/emscripten.h.html#c.emscripten_get_now)要求 get_now 返回毫秒。固定 4.0.10 SDK 的声明返回 double；本例使用 float overload 的正弦。若运行时确实使用该 adapter 的秒时钟，则正弦相位约为 `epoch毫秒/1,000,000`；本日期量级的 float32 步长约 0.125，相邻相位值对应约 125 秒真实时间，名义周期也被放慢约 1000 倍。

以导出文件名中的 epoch 毫秒作**代表值**进行纯数字计算，0、1、20、60 秒时的 float 相位均为 1792869.375，约 125 秒时才变化。该数字模型保存在 `CLOCK_STATIC_AUDIT.json`，不是手机时钟实测。运行时 adapter 是否因已有注入标记跳过、global performance 是否被覆盖或再替换仍未知，不能据此直接宣布手机不变的根因确定。

主循环静态路径为 main_loop(fps=0)→全局 RAF→runIter→再次 scheduler；adapter 转发现有 RAF，未发现可证实的调度遗漏。唯一明确取消分支是 drawing buffer size 查询失败并输出错误，当前日志无该错误。afterDoFrame 的注册日志位于注册调用前，不能证明后续 flush/batch/swap 执行，初始化摘要也只输出一次。
