# 编辑器面板简化需求（讨论记录）

分支：`claude/panel-simplify`，基于 `e682ce2`。本文只记录需求和已定方向，尚未改代码。

## 1. 用户原话要点

- 打开面板后，先让用户选择**小游戏输出目录**，或者把它保存在用户自己的游戏项目里，下次直接沿用。
- 常用的小开关直接放在面板首页，例如横屏/竖屏、是否启用 GLX、跳过预热。可以收起来，但不要藏进多层弹窗。
- 「官方引擎构建计划」「官方转换计划」里要填的东西太多。这些本该在底层配好，不应该让用户自己去找文件、考虑配置。
- 最简单的流程：打开面板 → 设置输出目录 → 选 **2D 模板** 或 **完整模板** → 需要时点「自定义」。
- 自定义时，用户点一下就能**一键检测**出游戏没用到、可以裁剪的功能。
- 插件也给其他开发者用，需要简短引导。

## 2. 现状问题（以 e682ce2 为准）

从打开 Godot 到在微信开发者工具中打开项目，需要约 11 次主按钮操作、3 个弹窗、约 15 个字段：

1. 「新建 PCK 导出计划…」填 7 项 → 「保存本地选择」→「只读计划」→「准备执行…」→ 确认 →（手动）「刷新本次执行收据」。
2. 「新建官方转换计划…」选配方、引擎 JS、WASM、转换器 exe、接口 JS、输出父目录，再填输出名、游戏名、语言、模式、横竖屏和可选项 → 再走一遍保存、计划、执行、确认、刷新。
3. 「在微信开发者工具中打开工程…」→ 可选 AppID 来源 → 确定。

具体问题：

- **固定文件让用户手选。** 安装版已经带有 `engines/full`、`engines/conservative`、`engines/pure-2d` 三组 JS/WASM 配对和 `tools/wx-transformer-v1.0.35-win.exe`，见 `release/profiles.json`、`packaging/vendor-lock.json`。面板仍要求用户每次去选这些文件。
- **自建引擎构建表单暴露在首页。** 它要求选 Emscripten SDK、配方、裁剪配置、并行数、预算，这些属于维护者操作。
- **内部概念外露。** 「保存本地选择」「只读计划」「收据」「任务 ID」在每个阶段都要手动操作。
- **说明文字常驻。** 顶部有 3 行免责说明和 2 行状态图例，每个弹窗也都有 3 到 4 行说明。
- **入口没有顺序。** 首页约 10 个入口按钮和 9 个操作按钮平铺，日常和高级功能混在一起。
- **状态不显眼。** 状态只写在一行小字里，需要手动刷新。

## 3. 已定方向

| 事项 | 决定 |
|---|---|
| 任务状态 | 只在本面板发起的任务运行期间自动刷新，到终态停止 |
| 资源分包 | 6 到 7 个入口合成一个「资源分包（可选）」折叠组，组内按步骤编号，默认收起 |
| 使用者 | 也给其他开发者用：每步一行引导，风险说明放进确认框和悬停提示 |
| 自建引擎构建 | 移出首页，放进「高级」折叠组 |

- **底层安全边界不变**：仍是共享 CLI 的只读计划、计划摘要、确认后执行；保存选择、读计划、带摘要执行由面板在后台串起来。

- 三个设置组都可折叠，标题直接显示当前取值；完整的组默认收起，有缺项的组展开并带 ⚠，有未保存改动的组带 ●。
- 分包场景放在「打包方式 → 资源分包 → 按场景分包」下面，和其他设置一起保存，不再单独保存。

- 「高级 → 最近运行」列出输出目录里的运行（含命令行和以前会话发起的），可打开、取消未结束的、在文件夹中显示、移到回收站。它取代旧面板「打开已有任务」中针对快速流程运行的部分；按任意请求文件打开任务仍在旧面板。
- 「取消」只在导出并转换运行时出现，确认后走快速流程的 `cancelQuickRun`：写取消标记并取消正在执行的共用任务，不回滚。

### 4.1 AppID 入口

- AppID 在状态卡里常驻显示（可部分遮挡，如 `wx12…cdef`），设置收起时也能看到。
- 设置区提供直接填写框，并保留「从已有 `project.config.json` 读取」作为另一种来源。
- 填写后需点「保存」才算生效；只做格式检查（`wx` 开头加 16 位十六进制），不代表 AppID 已在微信后台有效。
- 现状差异：当前 AppID 只在「打开开发者工具」时从已有 `project.config.json` 绑定，转换阶段不配置 AppID。改为转换前必填，需要在面板层做门禁，并确认与共享 CLI 的「用户 AppID 来源」检查一致；手填 AppID 如何作为合法来源记录，待实现时设计。
- AppID 属于本机或个人信息，按保存位置规则处理，默认不写进随项目提交的配置；如用户选择跟随项目保存，需明确提示。

### 4.2 前置条件：没填好就不能进入下一步

原则：**用户没有填好或保存好必需选项，下一步的按钮就不可点**，按钮旁或状态卡「还差」一行写明缺什么，点击缺项可直接定位到对应设置（设置区收起时自动展开）。

| 按钮 | 必须满足 |
|---|---|
| 导出并转换 | 已选模板；已选输出目录；AppID 已填写并保存；设置区没有未保存的改动；资源分包区没有未保存的改动；当前没有正在运行的任务 |
| 在开发者工具中打开 | 已选模板；AppID 已保存；本次设置下已有成功的转换输出；当前没有正在运行的任务 |
| 自定义 → 构建 | 已完成一键检测并确认裁剪项（详见第 5 节） |

- **未保存改动的判断**：设置区、资源分包区、AppID 任一处改了但没点保存，都视为未保存；对应分组标题显示「● 未保存」，并提供「保存」「放弃改动」。
- **设置变化使旧输出失效**：保存了新的模板、方向、GLX、预热或 AppID 后，之前的转换输出不再算「本次设置下的成功输出」，需重新导出并转换才能打开。
- **按钮只是面板层的拦截**：底层共享 CLI 的计划、确认、预算、路径检查照旧执行，面板拦截不替代它们。

### 4.2.1 设置置顶、未完成时锁住下方

- 设置区放在面板最上面，标为「① 设置」。首次打开或必填项未保存时自动展开。
- 模板、输出目录、AppID 三项未保存前，下方的状态卡以外区域（主按钮、资源分包、功能支持、高级、日志）整体变灰且不可点，并显示一行提示。
- 保存完成后设置区自动收起，标题显示摘要，例如「① 设置：完整模板 · 竖屏 · GLX」。

### 4.2.2 资源分包与转换的先后（现状）

按现有代码，资源分包不是转换后的独立附加步骤，它要求在转换**之前**改动游戏工程和 PCK：

1. 接入加载脚本：往游戏工程写入 4 个接收脚本和 `WxResource` Autoload（`lib/resource-project-install-task.mjs`）。
2. 导出完整 PCK。
3. 拆包：按用户声明把条目分到 boot 包和若干 resource 包。
4. 运行时依赖：为每个包指定入口场景或「仅挂载」，以及文件依赖，生成资源配置 JSON。
5. 资源接口计划：根据资源配置和引擎 JS/WASM 生成本次游戏的接口 JS。
6. 官方转换：使用拆出的 **boot PCK** 和上一步的接口 JS。
7. 最终组包：复制转换输出，把各 resource PCK 作为微信分包加入，并在 `game.json` 的 `subpackages` 里追加对应条目（`lib/resource-runtime-assembly.mjs`）。

所以资源包进入小游戏工程的方式是第 7 步：写入分包目录，并登记到 `game.json`。

新版做法（已定：放进第一步设置）：

- 「① 设置」里加「资源分包：不分包 / 分包（按场景延后下载）」，默认不分包。
- 选「分包」并保存后，下方出现「② 分包场景」。用户只选要延后下载的场景，未选并保存前不能导出并转换。
- 点「导出并转换」时，面板自动跑第 1 到 7 步；第 1 步写游戏工程前单独确认。

### 4.2.3 分包操作的简化

现状需要用户逐条把 PCK 条目分到各包、为每包选入口场景、手写 `res://来源 -> res://依赖` 文件依赖，并勾选「已手工核对」。简化为：

| 现在用户要做的 | 新版 |
|---|---|
| 读取 PCK 清单，逐条移动条目 | 只选场景；每个场景自成一个分包，包名由场景文件名生成 |
| 为每包选择入口场景或「仅挂载」 | 选中的场景就是该包入口 |
| 手写文件依赖 | 插件在编辑器内用 `ResourceLoader.get_dependencies` 递归分析，自动带上依赖 |
| 判断共用资源放哪里 | 被多个分包或首包用到的资源自动留在首包；脚本和工程元数据按现有规则留在首包 |
| 分别打开 6 个表单执行 | 合并进「导出并转换」一次完成 |

限制与仍需用户做的事：

- 静态分析找不到代码里用字符串动态加载的资源（如 `load("res://levels/" + name)`），界面要明确提示，并允许手动补充。
- 游戏代码必须在进入分包场景前调用 `WxResource.load_pack("包名")`，插件可提供示例代码，但不自动改游戏逻辑。
- 自动分析的结果仍交给共享 CLI 的拆包计划核验，计划不通过就不能执行。
- 现有拆包按 PCK 内的导出路径（含 `.remap`、导入产物）工作，编辑器里的源路径到导出路径的对应需要在实现时处理。

预览版状态：已能选择场景、显示每个场景的分包名、依赖数和共用数；尚未接入拆包执行。依赖分析在没有场景的工作台工程里只验证了空结果，需要在真实游戏里检查。

### 4.3 手动任务

- 现状：首页的「已有 REQUEST JSON / 已有任务目录 / 任务 ID / 保存本地选择」以及「只读计划、已有任务状态、准备执行、准备取消、刷新收据、使用本次任务」这组控件，用来对**任意一个已有任务**做查看、执行或取消。主要用途有两种：接着处理命令行或上次会话创建的任务；查看或取消面板重开后不再跟踪的任务。
- 新版：日常流程由面板自己记录并跟踪它发起的任务，用户不需要接触这些字段。这组控件整体移到「高级 → 手动任务」，默认收起，界面改名为「打开已有任务」，用于排查和恢复。

### 4.4 能力清单

- 现状：`lib/capabilities.json` 有 25 项，面板只用一个列表显示「名称 — 状态」，限制说明只在悬停提示里，没有分组；状态用「待核查 / 未实现 / 已实现待验证 / 当前配置不支持」这类内部措辞。
- 新版：
  - 改名为「功能支持」，按类别分组：渲染、输入、音频、网络、存档、登录、资源、引擎与构建、插件。
  - 状态用颜色和图标：已实现待验证（黄）、不支持（灰）、未实现（红）、待核查（灰蓝）。列表内直接显示一行限制说明，不必悬停。
  - 设置区的开关旁就近显示对应能力的状态，例如 GLX 开关旁显示「GLX 渲染：已实现待验证」。
  - 能力状态仍只来自 `capabilities.json`，面板不自行声称「已验证」。

## 5. 「自定义 → 一键检测可裁剪功能」现状与缺口

- 现有能力：`node wxslim.mjs official custom-project-plan FEATURES.json BOOT.pck` 和 `convert/lib/custom-project-usage.mjs` 会读取启动 PCK，并列出将被移除的模块和类，但「是否真的没用到」仍要作者**手工声明**（`removedFeaturesUnused`）。代码注释明确说解析 PCK 只证明文件身份，不证明用途。
- 缺口：目前**没有**自动扫描游戏使用了哪些引擎类或模块的功能。
- 待设计：扫描 PCK 或源工程里的场景、资源类型和脚本引用，给出「检测到使用 / 未检测到 / 无法判断（动态加载）」三类结果，再生成裁剪建议。扫描结果只是建议，不等于证明，动态加载和字符串反射需要提示。
- 自定义裁剪需要重新编译引擎，属于大型编译，按 CLAUDE.md 需逐轮授权；首页的「自定义」应先给出检测结果和预计体积，再引导到构建。

## 6. 待定问题

1. （已定，见下方「项目设置保存位置」）
2. 「保守」模板是否保留在首页，还是只留「完整 / 2D / 自定义」。
3. 输出目录是选一个固定目录每次覆盖，还是每次生成新子目录。现有规则拒绝写入已有输出，因此需要设计命名或清理方式。

6. 「一键检测」先做 PCK 级扫描，还是直接读源工程。

### 项目设置保存位置（已定：由用户选择）

「项目设置」指每个游戏要记住的选择：输出目录、模板、横竖屏、GLX、跳过预热、AppID 来源、游戏名、语言。现有 `local-config.json` 只记 Node、编辑器路径和上次任务，不记这些选择。

面板设置区提供「设置保存位置」选项，由用户决定：

| 选项 | 位置 | 适用场景 | 注意 |
|---|---|---|---|
| 跟随项目 | `res://` 下的配置文件，如 `res://wxslim.json` | 团队共享、换电脑仍保留 | 导出过滤必须排除该文件，不能进 PCK |
| 仅本工程本机 | `.godot/wxslim/` | 不想改动项目文件 | `.godot` 通常不进版本库，换电脑丢失 |
| 仅本电脑 | 插件本机状态目录（现有 `local-config.json` 旁） | 完全不碰游戏项目 | 只在本机有效 |

- 默认值待定。建议默认「跟随项目」，但本机绝对路径（输出目录、AppID 来源）始终另存在本机状态目录，避免团队成员互相覆盖。
- 切换保存位置时提示是否迁移已有设置，不静默删除旧文件。
- 读取顺序和冲突处理（例如两处都有设置）待实现时定。

## 7. 必须保留的约束（CLAUDE.md 第 2 条）

- 沿用共享 CLI 的请求 schema、状态码、确认摘要、取消边界和配对审核。
- 保留路径冲突、用户 AppID 来源和空间预算检查。
- 编辑器文件继续排除出游戏 PCK；任务日志在游戏缓存之外。
- 界面修订不自动获得引擎或设备验收结论。

## 8. 建议实施顺序

1. **第一版布局重组**：只做首页布局，包括状态卡、设置区、折叠组；配对和转换器从安装版自动带出。不改 CLI。
2. **一键流程**：在面板内串起保存选择、读计划、执行、自动刷新，确认框合并为一次。
3. **项目内设置**：在第 6 节第 1 条定下保存位置后实现。
4. **自定义与一键检测**：先出扫描设计和测试夹具，再接入构建流程。
